## 3. Real backend execution path traced

Status: VERIFIED

The real backend path used in the local app is the application review service and the coordinator pipeline, not a mocked standalone harness.

Actual flow observed:

1. Request enters the backend review service (`ReviewService.review_text()` in `Backend/engano_backend/review_service.py`)
2. The active brand and policy are resolved from the configured `ReviewSettings` and repository
3. Persistent brand memory is loaded if available, but remains advisory and cannot override authoritative policy
4. `CoordinatorAgent.run_review()` executes deterministic rules and specialist checks
5. The active provider is resolved and invoked (`gemini` in the local runtime)
6. Findings are aggregated and validated
7. A rewrite decision is generated by the rewrite agent
8. Post-rewrite revalidation executes over the rewritten draft
9. Final `ReviewResult` is returned with decision, findings, rewritten draft, and post-rewrite findings

The actual backend path was exercised with real calls through the service entry point using controlled non-sensitive drafts.

## 5. RED safety verification

Status: VERIFIED

The core safety invariants were checked against the implementation and exercised via real review execution:

- A rewrite proposal cannot override a RED decision: VERIFIED
- Unfixable critical violation remains RED according to the existing rules: VERIFIED
- The rewrite agent does not independently approve its own output: VERIFIED
- A clean-looking rewrite is not treated as proof of compliance by itself: VERIFIED
- The final decision reflects the actual authoritative outcome and policy constraints: VERIFIED
- Provider errors cannot masquerade as a clean review: VERIFIED
- Missing or incomplete revalidation cannot produce false GREEN: VERIFIED

This is enforced in the coordinator logic in `ai_engine/agents/coordinator.py`, where a RED decision forces reviewer approval and where rewrite output is only advisory; it does not replace the original decision semantics.
